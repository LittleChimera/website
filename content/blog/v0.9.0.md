Two components ship in this release: rollout-controller v0.9.0 and rollout-dashboard v0.9.1, with chart kuberik 0.6.0 pinning both. The dashboard gets a new home page, a GitHub-backed Changes view, and inter-service contract gates from the controller.

<!--more-->

## rollout-dashboard v0.9.1

The dashboard now answers the developer's question, not only the operator's: **is my change in yet, why not, and when, for every service it touches.**

**Changes.** `/changes` lists every merged pull request and commit across the repositories the cluster deploys, newest first. Your own changes come first; below them, one card per repository with its progress. Every row carries a DEV · STG · PRD meter: green means live there, amber means held there, a gray clock means waiting its turn, dashed means not there yet. Next to it, the one fact that matters ("held in dev on hello-api-app") and how long it has been in that state.

![Changes — your merged changes with a per-environment meter, and one card per repository](/screenshots/dashboard/changes.png)

**One page per change.** Open a pull request or a commit and the page leads with what holds it and what unblocks it: the rule, its constraint ("waiting on hello-api-app to ship api ^1.68.0, it is on 1.67.0"), and the action. Under that, a grid of every rollout that would receive the change, then a card per service with the same stage rows the rollout detail draws. Superseded and rolled-back commits read as what they are. Check-runs on the merge commit appear in the head band.

![A change — the hold, its constraint, the action, and every rollout that would get it](/screenshots/dashboard/change.png)

**Home is new.** The landing page is now a control centre rather than a list: the fleet's verdict in one line, then three sections in the order that needs attention. *In motion* shows what is deploying or checking right now, with its stage and what comes next. *Held* shows every rollout a rule is holding and what it waits for. *Steady* is everything on its newest build. Beside them, a rail: your changes, how it is going (deploys this week, typical time to production, failures), and recent activity. On a phone the rail leads with your changes.

![Home — in motion, held and steady rollouts, your changes, how it is going](/screenshots/dashboard/home.png)

**GitHub integration.** The dashboard signs each user in to GitHub through a GitHub App, so everyone sees exactly the repositories they can already read and nothing is stored server-side. Connected, it turns shas into things people recognise: pull request titles and authors on Changes, the commits and diffstat between the running build and the one you are about to ship in the Change Version dialog, commit changelists on a rollout's history, check-run results on a change's merge commit, and "View on GitHub" links that target the commit, not the tag. Setup is a client id and secret on the hub; see [GitHub integration](/docs/integrations/github/#dashboard-commit-changelists).

![Rollout history — a deploy in flight with the commit it ships, its diffstat and author, from GitHub](/screenshots/dashboard/history.png)

**Search.** Paste a PR link, `owner/repo#4`, `#4` or a commit sha into `⌘K` and land on the change. Free text matches the titles of your merged changes.

**What counts as a change.** A change's services are the ones CI released it for. A commit without a release for a service is not shown for that service; the dashboard does not guess why a build is missing. Failed-build detection is future work and documented as such.

**Also in 0.9.** A coverage bar on every build showing how many places run it and how many moved past; one page per repository; every page uses the full width of the viewport; "View on GitHub" links target the commit; a dead spoke no longer costs every hub request its full timeout; pre-release tags publish as pre-releases. `/revisions`, `/versions` and `/pr` redirect to `/changes`.

The dashboard talks to GitHub as the viewing user through the GitHub App, so a change is only visible to people who can see its repository. See [Connect GitHub](/docs/integrations/github/).

## rollout-controller v0.9.0

**Inter-service contract gates.** A release can declare the contract version it requires from another service, and the controller holds it until that service has deployed a version satisfying the constraint. `hello-frontend` built against `api ^1.68.0` waits in every environment until `hello-api` ships 1.68 there. Constraints use full SemVer ranges. The dashboard names the dependency, the constraint and the version the provider is on.

**First deploys skip gates and health checks.** A rollout's first ever deployment is no longer blocked by gates or health checks that cannot have an opinion yet.

**Deterministic status.** Gate lists on `Rollout`, `RolloutSchedule` and `ClusterRolloutSchedule` status are written in a stable order, so an unchanged reconcile is byte-identical and no longer bumps `resourceVersion` on idle rollouts.

**Attribution.** Automatic deployments are attributed to the system, not to the last user who deployed by hand.

**Flux.** The image-reflector-controller API is consumed at v1.

## Upgrade

```bash {filename="upgrade.sh"}
helm upgrade kuberik kuberik/kuberik --version 0.6.0
```

The chart pins rollout-controller v0.9.0 and rollout-dashboard v0.9.1. There are no CRD changes that require manual steps.
