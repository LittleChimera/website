You merged the fix an hour ago. Someone asks if it is in production. You open six tabs and start matching version tags to commit shas to namespaces. Kuberik v0.9 replaces that with one paste.

<!--more-->

## Paste the PR. Get the answer.

Drop a pull request link into the dashboard and it tells you, for every service the change touched, exactly where it stands: live in dev, live in staging, held in production. Not a checkmark. A reason.

![A change — what holds it, the exact constraint, the action that unblocks it, and every rollout that would get it](/screenshots/dashboard/change.png)

When something is held, the page says what holds it in one sentence, with the real constraint: *waiting for hello-api-app to ship api ^1.68.0, it is on 1.67.0*. Then it gives you the one thing to do about it. No runbook, no Slack thread, no guessing which rule fired.

Below that, every rollout that would receive the change, and for each service the same stage rows the rollout page draws. Superseded commits read as superseded. Rolled-back ones say so. If CI reported checks on the merge commit, they are right there in the head band.

## Every change you shipped, at a glance

`/changes` is the developer's view of the fleet. Your merged pull requests and commits, newest first, each with a three-dot meter for dev, staging and production. Green is live. Amber is held here. A gray clock is waiting its turn. Dashed means not there yet. Next to it, the one fact that matters and how long it has been true.

![Changes — your merged changes, each with a per-environment meter and the fact that matters](/screenshots/dashboard/changes.png)

Below your changes, one card per repository with its own progress, so a team lead can answer "how far did this week's work get" without opening a single rollout.

And the dashboard never guesses. A change's services are the ones CI actually released it for. If there is no build for a service, it is not shown for that service, and the page says so instead of inventing a status.

## A home page that starts with what needs you

The new home page sorts the whole fleet into three sections, in the order that deserves attention. **In motion**: what is deploying or checking right now, which stage it is on, what comes next. **Held**: every rollout a rule is holding, and what it waits for. **Steady**: everything already on its newest build.

![Home — in motion, held and steady rollouts, your changes, how it is going](/screenshots/dashboard/home.png)

Beside them, a rail: your changes first, then how it is going this week (deploys, typical time to production, failures), then recent activity. On a phone, your changes lead.

## Your GitHub, your view

All of this comes from GitHub, signed in as you through a GitHub App. You see exactly the repositories you can already read, nothing more, and nothing is stored on the server. Once connected, shas become things people recognise: pull request titles and authors, the commits between the build you run and the one you are about to ship, the lines each one touched, and links that land on the commit rather than the tag.

![Rollout history — a deploy in flight with the commit it ships, the lines it changed and its author](/screenshots/dashboard/history.png)

Search follows the same idea. `⌘K`, paste a PR link, `owner/repo#4`, `#4` or a sha, and you are on the change. Type part of a title and your own merged changes come up.

## Contract gates: the hold your developers actually hit

The most common reason a change waits is not a schedule or an approval. It is another service. The frontend was built against API 1.68 and production still runs 1.67.

rollout-controller v0.9.0 makes that a first-class gate. A release declares the contract version it requires from another service, and the controller holds it in every environment until that service has deployed a version satisfying the constraint, with full SemVer ranges. The dashboard names the dependency, the constraint and the version the provider is on, and points you at the service that needs to ship.

Also in the controller: a rollout's first ever deployment no longer waits on gates and health checks that cannot have an opinion yet, status is written in a stable order so idle rollouts stop churning, and automatic deployments are attributed to the system rather than to the last person who deployed by hand.

## Upgrade

```bash {filename="upgrade.sh"}
helm upgrade kuberik kuberik/kuberik --version 0.6.1
```

Chart 0.6.1 pins rollout-controller v0.9.0 and rollout-dashboard v0.9.1 and installs the new `RolloutDependency` CRD. Skip 0.6.0: it shipped the controller without that CRD. Connecting GitHub is a client id and a secret on the hub; see [GitHub integration](/docs/integrations/github/#dashboard-commit-changelists).
